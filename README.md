## 기술적 고민

### 1. Photon 멀티플레이 동기화 설계

여러 클라이언트가 같은 방에 접속할 때 플레이어와 몬스터 상태를 일관되게 유지하는 것이 핵심 과제였습니다.

- **Master Client** 기준으로 몬스터 생성과 상태 관리를 집중시켜 중복 생성 문제를 방지
- **PhotonView / RPC / RaiseEvent**를 상황에 따라 구분해 사용 — 위치처럼 빈번한 동기화는 OnPhotonSerializeView, 이벤트성 처리(피격, 사망)는 RPC
- **Late Join** 플레이어에게 현재 게임 상태(몬스터 HP, 위치 등)를 전달하는 구조를 별도로 구성해 입장 직후 상태 불일치를 해결

### 2. ScriptableObject / JSON 이중 데이터 구조

게임 데이터를 두 계층으로 분리했습니다.

- **정적 기획 데이터** (아이템 스탯, 퀘스트 조건, 몬스터 스탯) → ScriptableObject로 관리해 인스펙터에서 수정 가능하도록 구성
- **유저 진행 데이터** (보유 아이템, 장비 슬롯, 퀘스트 진행 상태) → JSON 직렬화 후 Firebase Realtime DB 저장
- 데이터와 로직의 분리로 아이템·퀘스트 추가 시 코드 수정 없이 에셋만 추가하는 구조 구현

### 3. 3D 환경 성능 최적화

씬이 커질수록 렌더링 부하가 누적되어 Profiler 기반으로 병목을 짚어가며 최적화를 진행했습니다.

- **Object Pool** — 몬스터, 투사체 등 반복 생성 오브젝트에 적용해 GC 부하 감소
- **Occlusion Culling** — 시야에 들어오지 않는 오브젝트 렌더링 제외
- **LOD** — 거리별 메시 전환으로 원거리 폴리곤 수 절감
- **Static 설정** — 이동 없는 배경 오브젝트를 Static으로 설정해 배칭 적용

## 회고

**어려웠던 점**
- 멀티플레이 초반에 "어떤 클라이언트가 무엇을 결정하는가"에 대한 기준 없이 기능을 붙이다 보니 상태 충돌이 반복됐습니다. Master Client 중심으로 권한을 일원화하는 구조로 정리한 뒤 문제가 해소됐습니다.
- Late Join 처리는 게임 상태가 많을수록 전달해야 할 데이터도 늘어나 구조를 여러 번 다시 설계했습니다.

**배운 점**
- 멀티플레이는 기능보다 동기화 기준 설계가 먼저라는 것을 직접 경험했습니다.
- 성능 문제는 감으로 최적화하지 않고 Profiler로 병목을 확인한 뒤 수치로 개선 전후를 비교하는 습관이 생겼습니다.
- Jenkins 파이프라인 구성을 통해 반복 빌드 작업의 자동화 가치를 경험했습니다.
